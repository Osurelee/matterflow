# 通用事务管理平台 · 产品需求文档

版本：v0.5；日期：2026-10-12；状态：按用户澄清调整为个人分发记录与跟进；M3新规则待实现验收。

关联文档：[技术设计](TECHNICAL_DESIGN.md)、[实施清单](IMPLEMENTATION_PLAN.md)。

## 1. 背景与定位

用户希望将工作任务、生活安排、成长计划，以及交给别人处理但仍需跟进的事情统一管理。系统应降低记录成本，明确下一步行动，保留进展与结果，避免事项交出去后失去踪迹。

产品定位：以事项为核心、以行动和责任为驱动的通用事务平台。首页优先帮助用户决定现在要处理什么。

### 1.1 信息来源与决策状态

| 类型 | 内容 |
| --- | --- |
| 用户已表达 | 管理任务记录、流转、分发与跟踪；兼顾生活；多平台通用；本地部署。访问方式：2026-10-12 由“倾向 Tailscale 私有访问”改为“公网 Funnel 访问”（用户决策：手机不希望常开 Tailscale；首次实测因手机未开 Tailscale 无法访问 tailnet 私有页面） |
| 用户本次澄清 | 系统由本人使用；分发指本人记录应该交给谁，不要求同事使用；无需独立联系人管理或在线接收/转交流程 |
| 对话中的建议，作为本稿基线 | Web/PWA；Next.js、SQLite；统一事项；低成本起步；多人协作不再作为默认路线 |
| 本稿补充的产品默认值 | 单账号、处理方文本记录与本人跟进、五态生命周期、软删除、站内提醒、日期规则、备份指标 |
| 待实际验证 | 长期开机设备、远程网络可用性、浏览器安装体验、备份目的地与运行性能 |

后两类是为了让开发可以推进而提出的设计，不应视为用户已逐项确认。

### 1.2 成功标准

首版验收目标，而非已测结果：

- 已登录状态下，仅输入标题即可创建，保存后跨设备可查。
- 从首页可找出今天要做、已逾期、该跟进以及等待他人处理的事项。
- 每次状态、责任或日期变化有记录，能解释事项的当前情况。
- 不使用额外表格即可跑通“记录—整理—自己处理/记录交给谁—本人跟进—完成—回顾”。
- 上线前完成跨设备测试与一次从备份恢复；连续试用七天后记录遗漏事项和操作阻力，再决定扩展。

## 2. 用户与典型场景

V1 只有系统所有者一个真实使用账号。工作、生活、成长都是同一个人的管理范围；对接人、部门或机构仅为事项中的文本，不是系统账号，也没有访问权限。

| 场景 | 操作路径 | 成功结果 |
| --- | --- | --- |
| 临时想到更换滤芯 | 输入标题 → 进收件箱 → 选生活空间 → 定日期 → 完成 | 随手记，不被复杂表单阻挡 |
| 请物业维修 | 建事项 → 填写“交给谁：物业” → 记录等待原因 → 设周五跟进 | 周五看到提醒，知道该联系谁 |
| 自己提交申请后等结果 | 状态设等待 → 写“查询审批结果” → 设跟进日期 | 即使无截止时间也不会遗忘 |
| 英语学习计划 | 建成长项目 → 添加多个独立练习事项 | 能逐项推进和回顾，暂不自动生成 |
| 工作问题持续跟踪 | 建项目 → 按交付结果建事项 → 写进展 → 核实后完成 | 责任与变化有记录 |

## 3. 产品原则与范围

1. 创建只要求标题，其余按需补充。
2. 工作、生活共用数据模型与流转规则。
3. 区分自己处理、交给别人处理和本人持续关注；本人始终是台账维护者，处理方仅记录在事项中。
4. 时间、风险、整理状态与事项生命周期分别表达。
5. 先实现能够持续使用的闭环，每个阶段都可独立验收。

| 版本 | 包含 | 本阶段不包含 |
| --- | --- | --- |
| V1 | 单账号登录、空间、项目、事项、处理方文本记录、本人跟进、时间线、搜索、站内提醒、回顾、导出、备份恢复、在线多端、PWA 安装验证 | 联系人库、接收/拒绝/转派/在线验收、多人注册/邀请、自动发消息、系统推送、离线保存、附件上传、子事项、日历看板、AI、复杂统计 |
| V1.1 | 本机草稿、离线新增与同步、冲突处理；评估系统通知 | 完整离线协作、静默覆盖冲突 |
| V2（候选，待个人使用验证） | 子事项、附件、日历/看板等个人管理增强，按实际需求选择 | 联系人管理、成员体系、接收/转派/在线验收、企业审批和公共注册 |
| V3 | 重复事项规则、自然语言录入、拆解建议、周期复盘 | 自动替用户承诺、未经确认的对外操作 |

V1.1/V2/V3 是规划范围，进入对应阶段前另行细化验收，不视为首版交付承诺。

## 4. 统一业务模型

### 4.1 对象定义

| 对象 | 含义及规则 |
| --- | --- |
| 空间 Space | 归属容器；V1 默认私人、工作、生活、成长，均仅本人可见；名称不等于共享权限 |
| 项目 Project | 同一空间内有共同目标的一组事项，可不设截止日期 |
| 事项 Task | 可行动或需持续跟踪的一件事；首版不再拆成两套“事项/任务”实体 |
| 进展事件 Event | 创建、修改处理方、状态变化、文字进展等不可直接改写的历史 |

复杂目标先用项目组织多个事项。未来子事项沿用 Task，不引入另一套生命周期。

### 4.2 事项字段

| 字段 | 默认/限制 | 说明 |
| --- | --- | --- |
| 标题 | 必填，去除首尾空白后 1–200 字符 | 拒绝全空白 |
| 描述 | 可空，最多 20,000 字符，纯文本 | V1 不支持附件或富文本执行 |
| 空间 | 默认私人 | 必须属于当前用户 |
| 项目 | 默认无 | 必须与事项同空间 |
| 状态 | 待处理 | 见生命周期 |
| 优先级 | 无；低/中/高/无 | 不强制填写 |
| 已整理 | 默认否 | 独立于状态，控制收件箱 |
| 处理方式 | 默认自己处理；可选交给别人处理 | 本人记录的安排，不代表对方收到或接受 |
| 交给谁 | 默认空；交给别人时必填，去空白后1–100码点 | 自由文本，可填姓名、部门或机构，例如“张三（工程）”“物业”；不关联联系人或账号 |
| 我关注 | 默认否 | 即使本人不执行仍要持续关注 |
| 计划日期 | 默认无，日期精度 | 表示准备哪天处理，V1 不做时间段排程 |
| 截止日期 | 默认无，日期精度 | 表示最晚哪天完成 |
| 下次跟进日期 | 默认无，日期精度 | 表示何时回来检查或联系；与截止日期独立 |
| 下一步动作 | 默认无，最多 500 字符 | 例如“问物业是否已预约师傅” |
| 阻塞原因 | 默认无，最多 1,000 字符 | 非空则标记阻塞；不改变生命周期 |
| 等待原因 | 默认无，最多 1,000 字符 | 进入等待中时必填 |
| 结果说明 | 默认无，最多 5,000 字符 | 完成时可选 |
| 时间与版本 | 系统维护 | 创建、更新、完成、取消、归档、删除时间及并发版本 |

“交给谁”只属于当前事项。修改一个事项不会改动其他同名事项，不建立身份关系、通讯录或批量改名。同名可通过部门等文字区分；历史事件保存修改前后文本。创建仍只要求标题，处理方式默认自己处理。

### 4.3 日期规则

V1 产品时区固定为 Asia/Shanghai；所有设备按此口径显示“今天”。业务日期为 YYYY-MM-DD，事件时间显示到分钟。

- 日期截止：本地日期超过截止日期且事项未结束，才算逾期。
- 跟进到期：下次跟进日期小于或等于今天；完成/取消后不提示。
- 允许填写过去日期；保存前给出说明，不擅自改到今天。
- 计划日期晚于截止日期时提示并阻止保存；两者任一为空不限制。
- 跟进日期晚于截止日期可保存，但提示可能无法及时处理。
- 到期只产生提示，不自动完成、转态或更改责任人。

## 5. 生命周期与责任规则

### 5.1 状态转换

活跃状态：待处理、进行中、等待中。结束状态：已完成、已取消。

| 当前状态 | 允许的目标状态 | 条件和副作用 |
| --- | --- | --- |
| 待处理 | 进行中、等待中、已完成、已取消 | 简单事项可以直接完成 |
| 进行中 | 待处理、等待中、已完成、已取消 | 退回待处理保留进展 |
| 等待中 | 待处理、进行中、已完成、已取消 | 离开等待时清空当前等待原因，历史保留 |
| 已完成、已取消 | 待处理 | 通过“重新打开”；清空当前完成/取消时间，原事件保留 |

进入等待中必须写等待原因；下一步和跟进日期建议填写但不强制。等待中没有跟进日期的事项进入回顾中的“等待但未安排跟进”。

完成和取消自动标记已整理、清空当前跟进日期；保留计划日期和截止日期用于回顾。完成可填写结果；取消必须填写原因。结束时保留处理方式和交给谁用于回顾；重新打开默认自己处理，清空交给谁、当前取消原因、结果说明及阻塞标记，不自动恢复旧处理安排或旧跟进日期；旧值保留在历史中，界面提示重新安排。对已归档事项重新打开时同时取消归档。

### 5.2 分发记录与本人跟进

“分发”仅表示本人记录应该由谁处理。系统不证明已通知、已接收或已执行；实际沟通发生在系统之外。

- 将处理方式设为“交给别人”时必须填写交给谁；保存只更新处理安排和历史，不自动改变事项状态、计划日期、截止日期或跟进日期。
- 可以先记“应该给工程部门”，保持待处理；实际沟通后由本人记录进展，需要等待时另行选择等待中并填写等待原因。建议填写下一步及跟进日期，不强制。
- 只改交给谁相当于本人修改安排，记录旧值/新值；不触发接收、拒绝、转派或责任生效机制。每个事项当前只有一段处理方文本。
- 改回“自己处理”时清空交给谁，旧值保留历史；状态和日期不自动改变。若仍等待外部结果，保留等待中也合法。
- 收到对方反馈由本人追加进展，根据实际情况决定继续等待、自己处理或完成；确认结果后由本人标记完成，不增加系统验收步骤。
- “我关注”独立开启，可与处理方式同时存在。交给别人处理的事项仍属于本人的台账与提醒。

### 5.3 整理、归档、删除

- 收件箱是“活跃且未整理”的查询，不是第六种生命周期。归属默认私人不算已整理。
- 点击“完成整理”移出收件箱；编辑归属、日期不自动移出。项目详情内创建则默认已整理并继承项目空间。
- 未整理的活跃事项可以出现在今天、搜索等视图中；重复出现是不同入口，不是复制数据。
- 只有已完成或已取消事项可以归档；结束后仍可在回顾查看，不强制立即归档。
- 删除移入回收站，所有正常视图隐藏；V1 不自动清空、不提供普通界面的永久删除。
- 恢复保留删除前状态和归档标记；恢复的活跃事项若已到期，重新出现提示。删除记录保留。
- 归档项目必须没有活跃事项；项目归档不自动改变事项状态，也不改变其归档标记。项目归档后禁止新增或移入事项。
- 含未删除事项或未归档项目的空间不能归档；默认私人空间不能归档。首版空间、项目不提供硬删除。
- 移动事项到其他空间时必须清空或重选目标项目；一次提交完成，避免出现跨空间关联。

### 5.4 边界操作补充（v0.4）

以下为本次验收补充的实现默认值，未改变单人首版范围：

- 已删除事项仅可在回收站读取和恢复；拒绝编辑、转换状态、修改处理方、追加进展等其他写操作。已归档事项只读，允许取消归档、重新打开或删除。
- 删除保留处理方式及交给谁，所有正常视图和计数排除已删除事项；恢复按原值呈现，不新增分发记录，也不推断对方已完成。
- 项目归档校验仅计算未删除的活跃事项。恢复事项或重新打开时，若原空间或项目已归档，返回409并说明需先取消容器归档；不得静默移动或自动取消项目归档。取消事项归档同样要求容器可用。
- 空间与项目提供取消归档操作；取消项目归档前须先取消所属空间归档。归档容器不能创建、移入或编辑事项，历史读取允许。
- 结束事项仍可修改标题、描述、归属、优先级、关注和结果备注；不能新增跟进日期或修改处理方式/交给谁，需先重新打开。完成/取消时保留处理安排快照，阻塞原因清空并保留历史。
- 处理方式与五态生命周期独立。“交给别人”可处于待处理、进行中或等待中；进入等待中不强制填写交给谁，例如等待快递到货。
- 追加进展必填，去空白后1–5,000字符；取消原因1–1,000字符。时间与日期必须是有效日历值，拒绝如2月30日。字符串长度统一按Unicode码点计数。
- “未安排日期”表示活跃事项的计划、截止、跟进日期全部为空；回顾默认包含已归档的结束事项，排除已删除事项。搜索不指定关系视图时查全部未删除未归档事项（含结束）；显式指定关系视图时与搜索条件取交集。

## 6. 信息架构与页面行为

桌面左侧导航，移动端保留“收件箱、我的事务、项目、回顾”主入口，空间筛选和设置放二级入口。全局可快速新增和搜索。首版以列表为主。

### 6.1 我的事务（默认首页）

以下视图均排除已删除、已归档和结束事项，“全部”指全部活跃事项；历史在回顾或搜索中明确开启。

| 视图 | 精确定义 |
| --- | --- |
| 今天 | 计划日期≤今天，或截止日期≤今天，或跟进日期≤今天；没有日期的不自动进入 |
| 即将到期 | 截止日期在明天至今天+7天，含边界 |
| 我要做 | 处理方式为自己处理；包含本人需要跟进的等待事项 |
| 交给别人 | 处理方式为交给别人；包括尚未沟通的安排，不能把此视图解释为已送达 |
| 等待中 | 状态为等待中，含未指定交给谁的等待 |
| 我关注的 | 我关注=true |
| 全部 | 所有活跃事项 |

今天视图按“逾期 → 跟进已到期 → 其余”分组，同一事项只出现在首个匹配组，但保留全部标签。组内按优先级高到低、相关日期升序、创建时间升序、ID 排序。相关日期为已填写的计划/截止/跟进日期中的最早值。其他事务列表采用同样的优先级和日期排序，空日期排最后；收件箱按创建时间倒序。

可叠加空间、项目、状态筛选。行内展示标题、状态、关联人、日期和风险；点击打开详情。列表完成操作提供短暂“重新打开”入口，其效果遵守重新打开规则，不假装恢复全部旧字段。

### 6.2 事项详情

上部：标题、状态、完成/重新打开操作。中部：归属、处理方式、交给谁、优先级、三类日期、下一步、原因与描述。下部：追加进展和历史时间线。

一次编辑用明确的保存/取消按钮。保存中禁止重复提交；失败保留当前表单；成功以服务端返回为准。退出未保存表单时提示。历史事件按时间正序展示，可分页查看更早事件；V1 不编辑或删除已有进展，写错通过追加更正。

### 6.3 项目、空间、回顾与设置

- 项目：名称、目标描述、归属空间、活跃/归档；查看关联事项并新增。完成数=已完成且未删除事项数，取消数单独展示，不把取消算完成。
- 空间：新建、改名、归档；同一用户下名称唯一。项目同一空间内名称唯一；均限制 1–80 字符，描述最多 5,000 字符。
- 事项处理方：在详情直接填写交给谁；选择自己处理时隐藏此输入。没有独立联系人页面、建立联系人提示、电话邮箱或邀请入口。
- 回顾：今天/本周/自定义日期内完成和取消的事项，按当前完成/取消时间过滤；周一为一周开始；另有未安排日期、等待未设跟进、已归档和回收站入口。
- 设置：账号退出、修改密码、时区说明、数据导出、最近备份状态；服务器恢复属于运维流程。

### 6.4 通用体验

空列表解释原因并提供新增或清除筛选入口；加载与空数据区分；错误提示提供重试。移动端 360px 宽度下不产生主页面横向滚动，主要触控区域目标≥44px；键盘可完成创建、编辑、关闭弹层，颜色之外使用文字区分状态。

## 7. V1 功能需求与验收

### 7.1 提醒和同步边界

V1“提醒”是站内标记与到期列表，关闭应用不会弹系统通知。跟进日期推迟操作要留下历史。V1 不做邮件、短信、微信推送和日历导出。

V1 在线轮询目标为前台每30秒，回前台和写入后立即刷新；可见时间受网络影响，不宣传即时同步。离线显示不可用/未保存状态，不显示“已同步”。已打开表单的文本在失败时保留于当前页面内存，但关闭、刷新可能丢失，离开前提示。离线持久化不属于首版。

## 8. 非功能需求

| 编号 | 目标与验收口径 |
| --- | --- |
| NFR-01 数据正确性 | 写入校验在服务端；事项和历史原子提交；重复请求不重复新增；并发不静默覆盖 |
| NFR-02 隔离 | 所有业务查询、写入和导出限定登录所有者；处理方文本不授予权限；不缓存私有响应供未登录使用 |
| NFR-03 性能 | 在最终部署机、1万事项/10万事件测试集、局域网条件下，列表/搜索/保存接口p95≤500ms，连续100次请求；首屏可操作目标≤3秒；分别记录冷/热启动 |
| NFR-04 可恢复性 | 默认每日备份，目标RPO≤24小时、RTO≤60分钟；以实际恢复演练验证；未确定备份设备前不算达到 |
| NFR-05 可维护性 | 数据迁移可追溯，部署配置与密钥分离，有健康检查与不含正文的错误日志 |
| NFR-06 可用性 | 验证实际手机/桌面浏览器，覆盖窄屏、键盘、失败重试、未保存提示；服务器停机明确报不可连接 |

## 9. 后续版本边界

当前路线持续服务于本人管理事项。多人登录、空间成员、接收/拒绝、转派和在线验收不属于已规划交付；只有用户将来明确提出真实共同使用需求时，才重新立项设计。不得为了假设中的多人协作增加当前交互负担。

V2候选为子事项、附件或更多视图，进入版本前按个人使用痛点排序。V3的AI仅生成可编辑建议；重复事项需明确时区、生成规则和去重。以上均不提前混入首版逻辑。
