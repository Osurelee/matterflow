# M5 独立事项、任意深度层级与引用 · 开发规格

版本：v0.6.2；日期：2026-10-13；状态：M5-01～08与M5-09已完成代码及本机隔离验收，正式库/设备/公网边界仍待后续阶段。依据：[PRD](PRD.md)第5/9/10节、[技术设计](TECHNICAL_DESIGN.md)、[实施清单](IMPLEMENTATION_PLAN.md)。本规格是M5的执行契约；旧“一层子事项”规则停止作为开发依据，历史验收报告保留。

## 1. 模型与不变量

1. 每条事项是一个Task，UUID永久稳定，拥有自己的标题、正文、状态、日期、处理方、附件、版本与事件。内容不嵌入父事项JSON，不因移动或启用项目能力重新创建，不依靠项目存在才能读取。
2. 全局捕获只要求标题或有效媒体，默认私人空间、无父级、无项目、未整理。用户不必预先判断任务/子任务/项目。后续移动只改关系与组织索引，保留内容和历史。来自项目/父事项的快捷创建可默认带上下文，但可选择无父级。
3. 主结构是一片树：每个Task最多一个直接父事项，可为NULL；无产品层数上限，不能自包含或形成循环。树之外使用引用表达多处出现，不把引用当第二个结构父级。
4. 同一主树同owner、同空间。空间是归属边界；项目是事项上的可选成果视图，分组是该视图的组织属性，不是基础事项类型。不能要求所有事项先属于项目。
5. 引用是独立关系记录，其target指向原Task。只展示该事项的紧凑内容、状态及打开详情入口；V1不递归展开引用目标的后代。因此引用可以交叉指向，界面不会循环展开。禁止自己引用自己，同来源/目标只允许一条有效引用。
6. 所有标题/正文/状态操作最终定位taskId；同一事项在主位置、引用位置、搜索或今天打开的内容一致。复制事项是另一个明确操作，不能用复制实现移动/引用。

## 2. 项目能力、分组及兼容

- 任意事项可以“启用项目视图”：为原Task创建projects扩展记录，projects.root_task_id唯一指向它；Task ID、正文、附件、历史保持原样。目标说明用该Task正文；完成标准、成果日期、暂停标记放项目扩展，不维护第二份项目正文。已有projects.description保留兼容，升级后编辑只用根Task正文。
- 项目根事项允许有主父级，也允许自身树内另一个事项启用项目能力。嵌套项目不复制内容；视图从对应根事项向下读取主后代，包含内部项目的事项，按ID去重。
- projects.status对外保留兼容：根Task done→completed，cancelled→cancelled，其余→active；暂停标记仅在根活跃时映射paused。改项目状态通过同一个根Task生命周期服务；暂停不暗改后代。不得让项目完成和根Task未完成长期分叉。项目归档/取消归档委托同一根Task主子树服务，在同一事务同步root与projects归档标记；不能归档Project后留活跃可写根Task。
- tasks.project_id是最近项目根（含自身）的兼容索引，**不是事项身份或第二个结构父级**。挂接/解除/移动/启用项目时在事务中重算受影响主子树。祖先项目视图用递归主关系查询，不用project_id相等代替完整后代。
- 分组仅安排某项目根的直接主子项。tasks.section_id只允许指向其直接主父级所启用项目的分组；其他层的Task为NULL。移动直接子项到另一分组改变section_id与顺序，其后代不逐项复制分组。引用区独立展示，V1不加入阶段分组。
- 旧项目迁移：为每个既有Project创建一条根Task（唯一新增对象），标题取项目名、正文取旧描述，状态按已知项目状态映射；原Project ID和原有Task ID不变。把原项目事项接到新根下，保留原section映射；原任务状态、媒体、修订和事件不变。项目名读取根Task标题；改旧项目名称API须调用同一根Task标题服务。
- 旧根Task生成时明确记录迁移事件/来源Project ID，不伪造旧任务创建历史。原tasks.project_id引用保持对应Project ID；迁移前后输出ID/数量/描述/事件/附件校验报告。已归档项目的根同步归档；若检测已有层级、重复root绑定、状态冲突或未知关系，迁移停止并报预检问题，不猜测覆盖。

## 3. 组织操作的交互与语义

| 操作 | 用户动作 | 确认后结果 |
| --- | --- | --- |
| 挂接已有事项 | 详情“组织→移到事项下”，搜索目标并预览路径/影响数量 | 原Task及主后代整体移动，taskId不变；无需先解除再提交 |
| 解除父级 | “移到顶层”，选择目标空间 | 主parent变NULL，后代关系保留；项目索引重算，无项目时为NULL |
| 同级重排 | 拖拽、上/下移动或菜单 | 只改主顺序，不改内容、状态与日期 |
| 跨空间移动 | 预览整棵主子树和空间变化，确认 | 主后代空间一起变；外部引用仍指原Task，不随主移动改来源空间 |
| 添加引用 | 详情“引用已有事项”，选择目标 | 新增关系；原Task不移动、不复制，不改变原处理方/日期 |
| 移除引用 | 引用行“移除此处引用” | 只软移除关系，原Task及其主结构不变 |
| 启用项目 | 原事项“启用项目视图”，填写完成标准等 | 原事项继续存在，增加Project扩展；后代不被打散 |

移动预览不是承诺：确认时需重新检查版本、目标路径与全部守卫。跨空间只允许本人可写空间。新目标及祖先须未删除、未归档；目标路径有已结束Task或已结束项目根时拒绝挂接活跃事项，明确列出需重开的祖先。为简化首版，挂接/重排也要求源与目标主路径可写；禁止把归档后代静默移走，先解除归档或单独整理。

移动集合包含仍保留主关系的软删除后代，连同其组织索引一并调整，保留删除标记和原批次，不将其恢复；若这改变了旧删除批次的结构快照，后续恢复须提示结构冲突。归档后代必须先明确解除归档，不偷偷解除。

主移动不自动整理收件箱、不重置日期/处理方、不标记完成。拖拽与菜单调用相同服务；手机用“移到…”和展开路径选择，不要求用户只靠拖动。

## 4. 生命周期、删除、恢复与引用

- 完成/取消某事项，服务端检查全部未删除主后代，任一活跃即拒绝并列出代表项/总数；已全结束仅提示父成果待核实，不自动关闭祖先。引用目标不进入这项守卫，避免共享引用把多个项目生命周期绑死。
- 创建、重开或恢复活跃后代要求全部主祖先活跃、未归档/删除，相关项目根可写；提示逐级重开，不隐式批量重开。正文或结果补充仍按既有“结束未归档可编辑”规则。
- 父级删除/归档提供两种明确选择：①先移动保留的后代再只处理当前项；②对预览集合整体操作。整体归档/删除要求集合中主事项都结束；不默默级联关闭，不包含外部引用目标。
- 删除采用软删除、batch_id及实际受影响ID快照，关联不物理抹除。恢复整批只恢复该次实际删除集合，不复活此前独立删除的后代；若删除期间有结构变化或原祖先不可用，拒绝并给出冲突，不能静默改父级。
- 单项恢复时全部主祖先可用，恢复活跃项还要求祖先活跃；不产生主关系孤儿。无普通界面永久删除。
- 原Task删除后各引用显示“事项已删除”；归档后显示归档只读状态，引用仍可打开历史。原Task恢复后引用自动恢复展示。创建引用要求来源可写、目标未删除且同owner；目标归档可被只读引用，来源已归档不能增删引用。移除一条引用不删原Task，软删除引用来源也不删目标。
- 引用区可打开原Task进行编辑，UI明确“修改会在所有引用处生效”；结束/删除原Task必须在原详情按主结构规则确认，不能把“移除引用”与“删除事项”放在同名菜单项中。

## 5. 展示、行动、计数与导出

- 树按需展开，默认不一次加载整棵树；某节点可聚焦为当前根。深层路径显示末几段与可展开完整路径，避免无限横向缩进。打开详情通过taskId，不依赖当前路径；移动后旧详情链接仍有效。
- 有未删除主后代的事项属于成果容器。没有未删除直接主子项的事项为有效叶子；全部主后代已结束但自己活跃的事项为待核实成果。引用不改变叶子定义。
- 今天/我要做/交给别人等主行动查询取有效叶子及待核实成果，按taskId去重。仍有活跃后代的到期父级以单独不计数提示显示；收件箱继续按每条Task自身未整理标记查询，不因挂接消失。
- 项目树/阶段进度统计未删除的主后代有效叶子，不计项目根自身、不计引用目标，不重复统计嵌套项目根与其叶子。完成、取消、活跃分列，空树显示尚未拆解。嵌套项目可在各自视图展示进度，不能将不同项目的总数直接相加称全局总数。
- 引用可连接跨空间/跨项目事项，但只作为相关事项展示，V1不参与项目进度/结项。原Task日期满足今天查询时，全局仅出现一次，不按引用数量乘算。
- 搜索默认按Task去重并附主路径/引用位置；移除引用后原事项仍可搜索。项目/分组结构筛选走主树，不能把引用目标误计为主成员。
- JSON/bundle导出Task、主parent/顺序、Project扩展、分组、引用记录及软删除批次集合；恢复保留原ID。CSV每Task一行，附主路径/项目根，引用位置按明确字段展示；不能用CSV声称无损恢复任意深度结构。

## 6. 数据与服务契约

- Task新增parent_id FK(tasks.id)、sort_key、structure_version（默认1）、deletion_batch_id；Project新增root_task_id唯一FK、is_paused等扩展。引用表task_references：id、owner_user_id、source_task_id、target_task_id、sort_key、version、removed_at及时间戳；唯一有效source/target配对。另存structure_batches的操作/成员快照，供审计和恢复。
- structure_version是主子树结构及本节点引用列表的聚合版本；创建/移入/移出/排序/添加或移除引用会递增相关source/旧父/新父，以及受影响主祖先链的结构版本，同一事务同一节点只递增一次。因此预览后深层后代被移走或挂入，也会让源子树根的结构版本过期，确认不能静默操作另一批后代。内容version沿用现有协议；移位Task及project_id/space_id/section_id实际变化的后代递增内容version并写组织摘要事件。
- 组织请求带requestId、源expectedVersion/expectedStructureVersion，及非空源/目标父的expectedStructureVersion。缺少版本返回400，过期409。同事务BEGIN IMMEDIATE重查递归祖先/后代、owner和状态，再批量提交关系/缓存/版本/事件/重放；互移A↔B并发只允许合法一方成功。
- 不新增图数据库或全量事件溯源；SQLite邻接表＋递归CTE处理主树。防环服务端检查，数据库触发器守住直接SQL绕过的owner/space/self/cycle不变量；所有结构API共用一套关系服务。
- 无固定深度拒绝值；读取分页默认50/最大100，迭代遍历或CTE，不在JS调用栈递归整树。操作超过资源预算返回可重试/需缩小范围的明确错误，整笔不提交，不自动截断后代，也不把资源限制伪装成业务深度上限。
- 建议读接口：GET /tasks/:id/children（直接主子项分页）、/ancestors（有界分页路径）、/references及/referenced-by；组织写接口：POST /tasks/:id/move（targetParentId可NULL、targetSpaceId、targetSectionId、position）、/references、/references/:refId/remove；项目能力POST /tasks/:id/enable-project。路由命名调整须先同步技术设计与测试。
- 整体删除/恢复/归档预览保存受影响ID及主边集合的摘要，确认时以structure_version及摘要复核；普通内容更新只用各Task的内容version，不必让全部祖先内容版本跟着变化。
- 根层排序的并发：无parent时使用space结构版本（spaces新增structure_version），根项创建/移出/移入/重排同样校验并递增；子项列表读取返回parent结构版本，根列表返回space结构版本。enable-project带原Task内容/结构版本，在事务内唯一约束防重复创建Project。

## 7. 交付顺序与验收实例

按实施清单M5-01→03→04→02→09→05→06→07→08执行；每项独立报告，不能只改类型定义或UI树就勾选完成。M3与M4已通过测试保留并回归，新关系模型不能追溯宣称已验收。

| 实例 | 必须结果 | 验收编号 |
| --- | --- | --- |
| 先捕获A，后放入B，再把B放入C | A/B ID、正文、录音、历史不变；C→B→A可导航 | AT-38/40 |
| 主链101层；移动中间节点到顶层 | 无固定层数拒绝，全部后代保留，分批读取可用，无横滚 | AT-38/40 |
| A挂B，B又挂A；两次同时互移 | 循环拒绝且无部分写入，并发至多合法一方成功 | AT-38/40 |
| A在B主位置，在C以引用出现 | C打开A并改正文，B同步读新正文；移除C引用后A不变 | AT-46 |
| 结束C但其中有活跃主孙项 | 拒绝，不能只检查直接子项；外部引用活跃不阻挡C | AT-39 |
| 移动父，已有一个后代此前独立删除 | 原删除标记不清空；整批删除恢复不复活先前已删对象 | AT-40 |
| 启用原事项项目视图；旧项目升级 | 原Task不复制，旧Project/旧Task ID保留，标题/正文来源唯一 | AT-41/47 |
| 树中A完成1次并有3个引用 | 全局完成计数1，主项目按叶子计数，引用不计结项 | AT-42/46 |
| 完整包恢复深层树、引用与图音 | 原ID/路径/引用/项目扩展/媒体一致，旧会话撤销 | AT-44 |

101层是最低压力样本，不是允许的最大深度。需另验证宽树分页、超时回滚、重复请求、移动后旧URL、跨空间、版本冲突、引用目标删除/恢复、祖先归档、内嵌项目与外部引用组合。测试仅在隔离库执行；上线前备份及迁移报告另验。
